## خلاصة المراجعة
- الخطة المقترحة **تتبع أفضل الممارسات** مقارنة بالوضع الحالي: إزالة inline handlers/inline scripts، تنظيم JS حسب الصفحة، وتفعيل CSP تدريجيًا.
- مع هدفك المستقبلي بالانتقال إلى **Twig**: تنفيذ الخطة الآن **مفيد جدًا** بشرط أن نضيف “تحضيرًا صغيرًا” في طبقة العرض يمنع تزايد الاعتماد على `include()` و الـ globals.

## ما الذي يجعل الخطة «أحدث وأعلى احترافية» من الحالي؟
- **CSP حديثة**: حاليًا لا توجد CSP فعّالة رغم وجود nonce + endpoint تقارير. الخطة تنقل المشروع إلى معيار حديث: Report-Only ثم Enforced، مع منع `script-src-attr`.
- **فصل مسؤوليات**: JS للسلوك في المتصفح، وPHP لمنطق الخادم؛ بدل مزج السلوك داخل HTML.
- **قابلية صيانة**: Controllers واضحة بدل شيفرات موزعة داخل Templates.
- **أداء**: تحميل JS حسب الصفحة + `defer`/Modules + كاش للأصول.

## توافق كامل مع الاستضافة المشتركة (بدون Node/Build)
- لا حاجة لأي تشغيل Node على السيرفر.
- الملفات الثابتة تُخدم كما هي، وComposer يبقى للخادم/التطوير كما هو الآن.
- التحسينات (ESLint/Playwright) اختيارية للتطوير فقط وليست شرطًا للتشغيل.

## توصية مهمة لهجرة Twig لاحقًا (بدون تغيير هدف الخطة)
- الوضع الحالي: ملفات `.tpl` هي فعليًا PHP تُنفّذ عبر `include()` وتعتمد على متغيرات عامة (globals)، وهذا أكبر عائق لـ Twig.
- لتسهيل الهجرة إلى Twig: نحتاج أن يكون لدينا **نقطة ريندر واحدة** بدل `include()` المنتشر.
- يوجد أساس قابل للبناء: `template()` و `App\Legacy\TemplateRenderer` موجودان لكنهما غير مستخدمين في المسار الأساسي.

## الخطة المُراجَعة (لا تُدخل Node، وتُسهّل Twig لاحقًا)
### 1) طبقة عرض موحّدة (View Rendering Adapter)
- إنشاء واجهة/مُشغّل ريندر واحد في PHP (Adapter) يُستخدم بدل `include()` المباشر تدريجيًا.
- في البداية: يظل يُدرج ملفات `.tpl` الحالية (لعدم كسر شيء).
- لاحقًا: نفس الواجهة تُحوَّل لتستخدم Twig `render()` بدون لمس بقية الصفحات.

### 2) تقليل الاعتماد على globals داخل القوالب
- بدل أن تعتمد القوالب على `$session/$village/...` ضمنيًا: نبدأ تدريجيًا بتمرير `context` واضح (مصفوفة بيانات) للـ template render.
- هذا يجهز القوالب للتحول إلى Twig لأن Twig يحتاج بيانات مُمررة صراحة أو globals مُعرّفة بعناية.

### 3) JS Architecture بدون inline
- إضافة `assets/js/app/bootstrap.js` كنقطة دخول.
- Controllers حسب الصفحة عبر `body[data-controller]`.
- Core صغيرة: dom/events/i18n.
- Bridge للقديم لإبقاء Popup/med_* تعمل حتى ننقل الاستخدامات في القوالب.

### 4) استخراج inline scripts الأولى
- البدء بالصفحات التي فيها inline scripts واضح (مثل index وnotification) ونقلها إلى Controllers.

### 5) إزالة inline handlers من Templates ذات التأثير الأكبر
- تحويل أنماط `onclick="return Popup(...)"` إلى `data-action` + تفويض أحداث.
- البدء بـ menu ثم Ranking ثم Build لأنها الأعلى تكرارًا.

### 6) CSP تدريجي (أفضل ممارسة)
- المرحلة A: Report-Only عبر ترويسة HTTP من نقطة مشتركة + nonce لكل طلب + report-uri إلى csp-report.php.
- المرحلة B: Enforced بعد انخفاض التقارير وإزالة أي سماحات مؤقتة.

### 7) أداء بدون Build
- `?v=filemtime(...)` لكسر الكاش عند تحديث الأصول.
- Cache-Control للأصول عبر إعدادات الخادم حيث متاح.

### 8) جودة دون Node
- JSDoc للواجهات العامة في core/controllers.
- الالتزام بـ DOM-safe APIs.
- الاعتماد على QA الموجود في المشروع لـ PHP.

## لماذا هذا يسهّل Twig لاحقًا؟
- لأننا نقلل تدريجيًا:
  - تنفيذ PHP داخل القوالب
  - الاعتماد على globals
  - إدراج القوالب من كل مكان
- ونستبدل ذلك بـ:
  - نقطة ريندر واحدة
  - بيانات واضحة تُمرّر للقالب
  - منطق في Controllers/Services بدل القالب

## مخرجات يمكن قياسها بعد كل مرحلة
- انخفاض عدد inline handlers/inline scripts.
- تقارير CSP تقل تدريجيًا.
- صفحات تعمل بنفس السلوك مع JS منظمة حسب الصفحة.
- بداية انتقال العرض إلى نمط أقرب لـ MVC مما يختصر تكلفة الهجرة إلى Twig لاحقًا.
